# DarkCall プロトコル仕様案

**開発の基準となる仕様案です。** 2026年10月4日にユーザーが実装と対象リポジトリへのcommit・pushを許可しました。以下の技術調査は開始前の記録です。実際の動作確認は[STATUS.md](../STATUS.md)に記録し、設計目標と検証済みの保証を区別します。

提案は、**出品者が同じ商品やサービスの枠を複数販売し、買い手が最大支払額を秘密にしたまま入札するZECオークション**です。仮称はDarkCall。Private Marketsに提出する想定です。運営自身が商品、流動性、常設の計算サービスを供給し続ける事業ではなく、出品者と複数の運営者が利用できるOSSのプロトコルとアプリを作ります。

最初に確認してほしい判断は次の3点です。

1. 商品は「同じものをK枠販売する、1入札につき1枠のオークション」で進める。

2. 資金は2-of-3の共同エスクローが預かる。ユーザーが単独で強制返金できる設計ではない。

3. 現実のZEC精算と証明を接続することを中核にする。接続が成立しなければ、単なる価格計算デモを完成品として扱わず、設計を見直す。

## 賞を狙う理由

狙う体験は、買い手が「自分の最大入札額を運営に渡さずに参加し、価格決定の正しさを検証し、shielded ZECで精算と返金を受ける」ことです。公開される価格や自分の当落から推測できる情報は、秘密の例外として最初から定義します。保証の対象は、資金付き入札に対して宣言したルールを秘密かつ正しく実行することです。本人の一意性や売り手の自作自演による価格操作は保証しません。売り手の偽装入札も原資Bを預ければ参加でき、原資の多くは返金されるため、資金の裏付けだけでshill biddingを防ぐことはできません。

審査で見せる価値は、秘密入札、検証できる価格計算、Zcashの資金移動が一つの実行につながることです。これはユーザーが提示したPrivate Marketsの「価格は公開、参加者は非公開」というテーマに合います。ただし、詳細な配点は確認できていません。この選択はテーマと技術的な完成度を重視した提案で、受賞確率の予測ではありません。

既存のMPCオークション研究やFROST資金管理を踏まえ、独自性の候補を「Zcashのshielded精算まで監査できるオークション」に置きます。世界初とは主張しません。関連研究の[Riggs](https://eprint.iacr.org/2023/1336)は比較対象であり、その仕組みをそのままZcashへ移せるという根拠にはしません。

## オークションのルール

以下は採用を提案するルールです。数値の上限や手数料は、実装開始後の測定で確定します。

| 項目 | 提案 |
| --- | --- |
| 出品 | 同じ商品またはサービスをK枠。初回デモはK=3 |
| 入札 | 1枚の資金付きチケットにつき1枠。最大支払額bを提出 |
| 入札上限 | 最初の測定は4件。提出版は最大32件を目標とし、実測で決める |
| 資金 | 全員共通の入札原資Bと固定の処理費fを入金。D=B+f |
| 金額の表現 | 計算はすべて整数zatoshi。表示だけZECに変換 |
| 成約 | 最低価格r以上の入札を額の降順に並べ、上位K件まで落札 |
| 価格 | 適格入札がK件を超えたらp=max(r,第K+1位の入札額)。K件以下ならp=r |
| 同額の順位 | プロトコルが導出した32-byte ticket IDを、符号なしバイト列の辞書順で比較。公平な抽選やgrinding耐性は保証しない |
| 支払い | 全落札者が同じpを支払う。w=min(K,適格入札数)、出品者の受取額はw×p |
| 返金 | 落札者はB−p、非落札者はB。処理費fは事前に表示する |
| 変更と撤回 | 最初の版では受付完了後の変更と撤回は扱わない。未受付の入金は返金対象 |
| 範囲 | 1チケット1枠。複数チケットの購入は可能で、1人1入札を保証しない |

例として、B=1 ZEC、K=3、r=0.2 ZEC、入札が0.9、0.7、0.6、0.5、0.3、0.1 ZECなら、上位3件が0.5 ZECずつ支払います。出品者への支払いは1.5 ZEC、入札原資からの返金総額は4.5 ZECです。この入札一覧は説明用の値で、本番では公開しません。

処理費の扱いも証明対象の計画に含めます。正常精算のnは受付済みの資金付き入札数、w=min(K,適格入札数)です。合計課金はw×p、返金総額はn×B−w×p、出品者の受取額はw×p、運営の受取額はn×f−Fです。n×(B+f)＝返金総額＋出品者受取額＋運営受取額＋Fを満たし、すべて整数として計算してoverflowと負数を拒否します。w<Kなら売れたw枠分だけを支払い、w=0なら出品者の受取額は0です。入金取引の手数料は参加者が別途負担します。中止と未受付の資金チケットの返金では、それぞれの返金対象チケット数を使い、課金と出品者受取額を0、原資返金をBとする別modeを明示します。処理費fの扱いも受付前に表示します。

### 手数料と取引形状の固定

開催時にfee_rule_idとshape_policy_idを条件ハッシュに含めます。初版の候補は、Ironwoodだけを使い、他のpoolとtransparent入出力を含めない取引です。DarkCall自身の規則として、ZIP 317 Revision 1の式F=5000×max(2,a) zatoshiを採用し、aはダミーを含む実際のIronwood action countとします。この式はwalletの推奨手数料であり、Zcash consensusがオークションの手数料規則を強制するわけではありません。[ZIP 317](https://zips.z.cash/zip-0317)。

提案するshape_policyは、n≥1の正常精算でn個の資金noteを消費し、返金n行、出品者1行、運営1行の計n+2出力枠を固定するものです。ゼロ額の行にも0値の枠を予約し、追加のお釣りや他の資金noteを混ぜず、a=n+2とします。精算行とaction indexの対応も計画にコミットします。これにより当落や返金額で取引の形を変えません。n=0では取引を作らず、Fと運営受取額を0とします。この形を採用SDKで正しく構築できるかは未検証です。ゼロ額の枠を含むnative取引の生成が最初の検証条件で、SDKが追加のpaddingやchangeを要求する場合はpolicyを修正してレビューに戻します。ゼロ額は着金を要求する支払いとは区別します。

受付rootとnの確定後、最終的なオークション証明を作る前にa、F、運営受取額n×f−Fを確定します。開催前に許容する各件数についてn×f≥Fとなるfを選びます。証明と署名者は固定した式と収支を検査し、公開検証者も実取引のpool構成、action count、手数料を照合します。証明後にFやaを変更する取引には署名しません。再構築が必要なら計画と証明を作り直します。中止と未受付チケットの返金は、返金集合と件数mを別に固定し、課金0、出品者受取額0、返金m×B、運営受取額m×f−Fというmodeで検査します。

### チケットIDの導出

同額順位に使うIDは、運営が自由に発番する連番ではなく、ticket_id=SHA256(domain、auction ID、network ID、pool ID、funding txid、action index、funding cmx、入札者の仮名公開鍵、返金先commitment)とする案です。domainはDarkCall/ticket/v1とします。全フィールドの順序、型、長さとバイト順を固定し、整数はlittle-endian、可変長部分は長さを付けます。txidはnode RPCのhex表示を復号した32-byte列、cmxはnative SDKの正規の32-byte表現を使います。IDの全32-byteを符号なしの辞書順で比較し、証明用fieldへの剰余変換によって別のIDを同一視しません。

入札者の仮名公開鍵と返金先commitmentは入金前のinvoiceで固定し、入金memoとの対応を管理者が検査します。同じfunding noteを別の鍵で再発行できないよう、資金台帳で一度だけ使用します。資金証明の署名者はIDを再計算してから証明に署名します。funding tuple自体は公開せず、一般の検証者には署名済みIDと必要なcommitmentだけを示すため、この導出の検査も初版では管理者の資金証明への信頼に含まれます。

ハッシュによる導出は、入札者が鍵やnoteの乱数を何度も試して有利なIDを探すことを防ぎません。複数の資金チケットも作れます。同額時の再現可能な順位を定める規則であり、公平な抽選、Sybil耐性、shill bidding耐性とは説明しません。

## 秘密にする情報と信頼条件

入札額を隠す対象と、資金管理者が必要とする情報を分けます。通常のZK証明では証明作成者が入札の平文を知り得るため、入札処理と証明作成の両方をMPCで行う案です。入札者が公開コードを確認できる信頼済みクライアントを実行することも前提です。運営が配信するWebコード自体を悪意あるものに差し替えられる場合、MPCだけでは端末からの漏えいを防げません。クライアントの配布と検証方法を実装計画に含めます。

| 関係者 | 見える情報 | 原則として渡さない情報 |
| --- | --- | --- |
| 一般の検証者 | オークション条件、受付済みチケットの仮名IDとコミットメント、件数、価格、成約数、証明、関連する取引 | 個別の入札額、個別の返金額、受取アドレス、実名 |
| 受付と精算の担当者 | 入金D、チケットとの対応、返金先、精算時の当落と支払額 | 最大入札額の平文 |
| MPCノード1台 | 入札のシェア、公開入力、計算と証明に必要なメッセージ | シェアから復元した全入札 |
| 入札者 | 自分の入札、自分の当落と返金、公開結果 | 他人の個別入札 |
| 出品者 | 公開価格、成約数、受取額、納品に必要な情報 | 入札額の一覧 |

**提案する最初のMPC構成は3ノードのREP3です。保証するモデルは最大1者のsemi-honest adversaryで、2ノードが結託すると秘密を復元できます。** 秘密保護の表示を「1-of-3 honest」としてはいけません。1者だけ正直で残り2者が結託すれば破れます。計算の可用性には全3ノード、資金の署名には2-of-3が必要で、秘密保護、署名権限、可用性を別々に表示します。 既存coSNARK実装を使う試作では、保守的にsemi-honestの範囲だけを保証対象にします。1ノードの能動的なプロトコル逸脱に対しても秘密が守られるとは、確認なしに主張しません。公開証明が正しくても、計算中の秘密漏えいが自動的に防げるわけではありません。[TACEOのモデル解説](https://core.taceo.io/articles/honest-majority-mpc-for-cosnarks/)、[malicious coSNARKの研究](https://eprint.iacr.org/2025/1026)。

資金は別の保証です。2-of-3のFROST署名者が預かり、少なくとも署名に参加する正直な管理者がルール違反の取引を拒否することを前提とします。2者が結託すると資金を不正に移せます。初版は同じ3運営者がMPCノードとFROST署名者を担当する案です。MPCと署名の鍵は別にし、それぞれの結託条件を表示します。エスクローのfull viewing capabilityは3運営者すべてに渡す案です。各者が入金noteを復号し、入金額、memo中のチケット関連情報、エスクロー内のnoteと消費状態を独立に確認します。outgoing viewing keyを使った出力の追跡範囲も、採用SDKの実装に合わせて記録します。viewing capabilityを閾値で秘匿する保証はありません。[鍵の役割](https://zcash.github.io/orchard/design/keys.html)を区別し、最大入札額とその開口はdeposit memoやPCZT、受付ログに含めず、MPCへのシェア送信経路だけで扱います。

精算担当者には当落と返金額が分かる設計です。公開価格が境界の入札額と一致する場合は、その値が公開結果として漏れます。少人数、同額入札、自分の当落、売り手による繰り返し開催から推測できる情報も残ります。IP、アクセス時刻、入金時刻を隠す保証は初版に含めません。

3プロセスを同じ開発者の端末で動かすデモは、独立した3運営者による秘密保護の証拠にはなりません。再現用のローカル構成と、別々に運用する場合の条件を区別します。

## 入金から返金までの流れ

1. **開催条件を固定する。** auction ID、ネットワークとpool、K、r、B、f、fee_rule_id、shape_policy_id、受付終了条件、精算期限、署名者とMPCノードの公開鍵、出品者受取先を確定します。条件のハッシュを入札と証明に含めます。確認済みのブロック高を基準にし、確認数とreorg時の扱いは実装開始時に決定します。

2. **shielded入金を資金チケットにする。** 共同エスクローは確認済みの受取noteについてDを確認し、auction ID、入札者の仮名公開鍵、返金先のコミットメントに結び付けた資金証明を署名します。同じnoteから複数のチケットを発行しません。これは最初の版では管理者による証明で、誰でも独立に入金額を検証できるZK証明とは区別します。

3. **端末で入札を作る。** bと十分な乱数をコミットし、シェアを各MPCノードに直接送ります。運営サーバー経由で平文を送らない構成にします。クライアントの妥当性証明で0≤b≤B、チケットとの対応、シェアのコミットメントとの整合性を示します。共有値の不一致を受付前に排除する具体的な入力方式は、最初の検証項目です。

4. **受付記録を確定する。** ノード側でシェアを検証できた入札だけに署名付き受付証を返します。受付証には条件ハッシュ、チケットID、入札コミットメントを含めます。締切時に受付集合のrootを固定し、証明はその集合を全件処理します。受付済み入札の除外は受付証で検出します。受付自体の検閲や、未受付の送信まで含めた完全性は保証しません。

5. **秘密のまま価格を計算し、証明する。** MPCで順位、p、当落、精算計画を計算し、coSNARKを作ります。最大入札額を復元して通常のproverに渡す方式は採用しません。精算担当者には必要な宛先と金額だけを渡します。

6. **証明と実際の取引を接続する。** 精算担当者がPCZTを作成し、署名者が証明、出力、手数料を検査します。精算計画とnative noteの対応を示す追加証明を作り、FROSTで署名してbroadcastします。初版の候補では出品者への支払いと全返金を、固定したshape_policyの同一取引に含めます。上限や費用で分割する場合は、完了条件を再設計してレビューに戻します。

7. **着金を確認する。** 公開検証者は証明と取引の確認状態を検証し、参加者は自分のwalletで復号したnoteの金額と受取先を確認します。取引の掲載、支払い内容の証明、walletでの受領確認を別々の状態として表示します。

鍵保有者が停止した場合の返金は、署名者2者による中止用の取引です。MPCは全3ノードが必要になるため、1ノード停止で計算が止まっても、資金管理の2者が動ければ中止返金へ移れるようにします。全管理者の停止や結託に対し、ユーザーが単独で返金を強制できる仕組みはありません。

## 証明が主張すること

### オークションの証明

公開入力は条件ハッシュ、確定した受付集合のroot、件数n、価格p、成約数w、精算計画のコミットメント、およびfee_rule_id、shape_policy_id、action_count、F、運営受取額です。秘密入力は入札額と乱数、受付された入札の開口、必要な順位情報です。

証明する条件は、受付集合と入力集合の一致、チケットの重複排除、金額の範囲、上位K件と同額順位ルール、価格式、各チケットの課金と返金、出品者と処理費の金額、資金収支の一致です。未使用の回路スロットは明示的に無効化し、ダミーが価格や成約数に入らないようにします。

この証明だけでは、受付前の検閲、架空の商品、入金の実在、実際の送金は証明しません。公開するstatementは、管理者が署名した資金チケットを前提とすることまで含めて説明します。

### 精算への接続

精算計画の各行を、出力種別、ticket ID、正規化した完全な受取先、zatoshiの金額、隠蔽用の乱数にコミットします。出品者、返金、処理費の各行を含め、出力の順序とゼロ額の扱いを一意にします。

追加の精算証明は、同じ計画への開口と、実際の取引のnative noteの開口を使い、「各計画行の宛先と金額が、その取引の出力コミットメントに一致し、行の欠落や使い回しがない」ことを示す設計目標です。公開検証者は証明で指定されたpool、取引、action index、note commitmentを、自分が信頼するZcash nodeのデータと照合します。 native出力は[実装](https://github.com/zcash/orchard/blob/main/src/note/commitment.rs)上、PallasのSinsemilla commitmentから取り出したx座標です。精算回路は同じ演算と正規のバイト表現を検証し、受取先、金額、noteの各値を計画に結び付ける必要があります。Ironwood固有のnote生成も[ZIP 2005](https://zips.z.cash/zip-2005)と採用するSDKで照合します。価格計算用のハッシュをnative commitmentの代わりには使いません。また、古い支払いを別の開催の精算として流用するケースを検証対象に追加します。auction IDと受付rootだけでなく、その開催の資金チケットの消費、取引の時期、確定状態を照合する設計を具体化します。

**この接続回路はまだ実装も測定もしていません。** Ironwoodのnote commitmentを外部の回路で検証する費用と、native暗号文の整合性をどこまで証明するかが、最大の技術的不確実性です。精算担当者は返金先と金額を知ってよいので、追加証明を単独で作っても、そこに最大入札額を渡す必要はありません。

note commitmentの一致だけでは、walletが正しく復号できることまで保証できません。最初は署名者によるnative暗号文の独立検査と、受取walletの復号確認を併用する案です。暗号文の正しさまで公開ZK証明に含められない場合は、その部分が管理者への信頼であることを残します。「誰でも全着金を秘密のまま完全に証明できる」という強い説明は、その条件を満たすまで使用しません。

Zcash consensusが検証するのはnativeの取引と署名です。アプリのオークション証明をオンチェーンで強制する設計ではありません。署名者が拒否する仕組みと、送金後に公開検証者が照合する仕組みを分けます。

## 先に検証する攻撃と失敗

| ケース | 提案する対応と限界 |
| --- | --- |
| 締切後の入札差し替え | 条件ハッシュ、確定root、受付証と照合し拒否 |
| 受付済み入札の除外 | 受付証による検出。rootの一貫性を管理者が検査 |
| 同じ資金で複数入札 | deposit noteとticket IDを重複排除 |
| 不正なシェアや範囲外の値 | 入力証明とシェアの検査後に受付。方式未確定のまま完成扱いにしない |
| 偽物の出品者入札で価格を釣り上げる | 資金付き入札は要求するが、売り手の自作自演や複数IDを排除しない |
| 間違った順位や返金 | オークション証明が失敗する |
| 正しい証明に違う取引を添える | 精算証明のnative出力との対応が失敗する。署名前の検査でも拒否 |
| 誤った暗号文や受領通知 | native暗号文検査と受取wallet確認。公開証明の保証範囲と区別 |
| 1つのMPCノードが停止 | 価格計算を中止し、資金管理者2者による返金へ移行 |
| 2管理者が結託 | 資金と入札の秘密を破れる可能性がある。初版の信頼条件 |
| reorgや取引期限切れ | 検証状態を巻き戻す。旧取引との競合を確認し、再構築して再署名 |
| 売り手が納品しない | 初版では解決しない。ZEC決済と商品の納品のatomic swapではない |

受付前の入金、遅延入金、不正入力により未受付となった入金も、返金台帳に残します。確定rootに入らなかったことを理由に資金を取り残しません。中止と正常精算の二重実行を防ぐ台帳と、実際に消費したnoteの照合も必要です。Dと一致しない誤額入金は資金チケットにせず、実受取額Vを別台帳に記録します。Bを返金する式を誤額入金に適用せず、返金費用と少額noteの扱いを、実装前に確定する運用条件として残します。

## 技術候補と確認済みの事実

| 部分 | 第一候補 | 現時点の確認 |
| --- | --- | --- |
| 価格計算と共同証明 | TACEO co-snarksのcoNoir | Noir回路の共同witness作成とUltraHonk系の証明実装が公開されている。実行は未確認 |
| クライアントの入力証明 | 同じNoir系の回路 | 共有値と入札コミットメントを結び付ける回路を設計する。単なるrange proofで代用しない |
| Zcash取引 | librustzcash、pczt、nativeのIronwood経路 | 既存部品を使う。アプリ側で独自の送金形式を発明しない |
| 共同署名 | Zcash Foundationのreddsaとfrost-tools | Ironwood v6の外部署名PRが2026年8月12日にmerge済み |
| 精算の追加証明 | 独立した回路で評価 | Pallas上のnative演算を使うHalo2系と、Noir系でnative演算を表現する案を比較。価格証明と同じ方式に固定しない |
| オーケストレーション | Rust | 秘密、公開情報、PCZTを別の型と処理経路で扱う |
| UI | TypeScriptのWebアプリ | 個人の入札端末、出品者、公開検証画面を用意する。UI着手は技術検証後 |

[co-snarks](https://github.com/TaceoLabs/co-snarks)は実験的な実装です。利用候補は調査時点のcommit `467a2abbad940d40ed78f38d424cc21920988976`。coNoirの[互換性の記載](https://github.com/TaceoLabs/co-snarks/blob/467a2abbad940d40ed78f38d424cc21920988976/co-noir/co-noir/Readme.md)にはNargo v1.0.0-rc.2とBarretenberg v5.0.0-nightly.20260522があり、最新同士を無条件に組み合わせません。使用する証明はZKを有効にしたvariantとし、通常の非ZK variantを秘密入札に使わないことも検証します。ライセンスは採用するsubcrateごとに確認します。公式の[Quick Start](https://docs.taceo.io/docs/getting-started/quick-start-co-noir/)には古いBarretenbergとNargoの組合せ、および基本のfield arithmeticのみという記述があります。一方、固定したcommitの[builder実装](https://github.com/TaceoLabs/co-snarks/blob/467a2abbad940d40ed78f38d424cc21920988976/co-noir/co-builder/src/ultra_builder.rs)にはrange、logic、Poseidon2などの処理があります。ドキュメントだけで必要なgateが未対応だと断定せず、固定commitのコンパイル結果と実際のMPC witness生成を検証します。実装の存在は、今回の回路の動作を確認したことにはなりません。

[FROSTのPR 593](https://github.com/ZcashFoundation/frost-tools/pull/593)には実取引によるtestnet検証の報告があります。調査時の[Cargo設定](https://github.com/ZcashFoundation/frost-tools/blob/main/Cargo.toml)はorchardのforkと`unstable-frost`を利用しているため、安定版だけで無修正に完成すると扱いません。既存実装の報告と、私たち自身の動作確認は別です。

[PCZTの仕様](https://github.com/zcash/zips/blob/main/zips/zip-0374.md)は、受取先や値などの秘密情報を含み得ることを説明しています。PCZTを公開結果や通常のログに載せません。

ZSAとZIP 228は初版の必須依存にしません。[ZIP 228](https://zips.z.cash/zip-0228)は固定の交換条件を持つswapの仕様で、価格決定後の柔軟な部分約定をそのまま解決するものではありません。初版はZECで商品や枠を買うオークションです。ZSA同士の非カストディ交換は別の設計判断にします。追加調査では、QEDITの[2026年5月5日の報告](https://forum.zcashcommunity.com/t/zcash-shielded-asset-swaps-and-transaction-acceptance/48432/52)と、専用の[zsa-swap branchのテスト](https://github.com/QED-it/zcash_tx_tool/blob/zsa-swap/src/commands/test_asset_swaps.rs)を確認しました。swap実装が存在する根拠であり、私たちの動作確認ではありません。調査時のbranch commitはa344fde10418ac824bf66662bb3a39dba61b213fです。秘密の価格決定後に未知の価格と約定量を反映するには、再承認などの設計が必要です。取引者が結果を確認してオンラインで再承認する候補はありますが、署名拒否による不成立と、matcherに実約定量を見せない構成も別途検証します。ZSA案へ変更した場合は、可変数量の売買注文、資産の交換、売買両側の署名、部分約定が加わります。現仕様の共同エスクローによる商品購入と、同じ保証であるとは扱いません。

## 実装開始後の最初の判定

最初の48時間を技術検証に割り当てる提案です。ここは作業予算であり、成立を予測する約束ではありません。開始後はAの秘密入札と共同証明、Bのnative入金と共同署名、Cの精算への結合を並行して検証する計画です。Dの統合では、先に条件ハッシュ、受付root、精算行の正規化とコミットメント、公開入力の形式を共通仕様として定めます。A、B、Cが独自のデータ形式を作って後から合わせる進め方は避けます。最初の到達点は4入札の全工程とし、32件はその後の測定目標です。32件を完成条件にはしません。48時間の判定には、Cも接続方法の説明だけでなく、最小の実証明の生成と検証を含めます。

| 検証 | 合格条件 |
| --- | --- |
| 秘密入力と共同証明 | 4入札のシェアを別ノードへ入力し、witnessを平文に復元せずに価格証明を生成。通常verifierでも検証できる |
| 入力の整合性 | 不一致シェア、範囲外の値、重複チケットを受付前に拒否できる。正しい参加者の入札額を公開しない |
| native資金管理 | 2-of-3でtestnetのIronwood受取、支出、返金を再現し、違う宛先や金額への署名を正直な管理者が拒否 |
| 精算との結合 | 1入札者の返金計画を実際のnative出力に結び付ける最小証明を測定。宛先、金額、別取引への差し替えを拒否 |
| walletの受領 | 関係する受取walletがnative noteを復号し、金額を検証できる |
| 必要資源 | 回路と証明の時間、各ノードのpeak RAM、MPC通信量に加え、取引byte数、実action count、実際のZcash手数料を測る。4件の全工程後に32件目標を見直す |

これらが通れば、オークション一回の全工程を実装します。精算証明が過大、入力方式が安全に成立しない、native署名が接続できない場合は、原因と代替案を提示します。通常のproverに入札一覧を渡したり、単独管理者の残高表示だけに置き換えたりして、同じ保証があると説明することはしません。

本命の提出目標は、精算計画とnative出力を結ぶ公開ZK証明を含む方式Aです。研究リスクに備え、方式BはオークションZK証明と独立したPCZT検査、および運営者2-of-3による公開attestation、方式CはオークションZK証明と実送金、および各受取walletの確認として区別します。Bのattestationは、auction ID、受付root、plan commitment、feeとshape情報、networkとpool、txidまたはeffects digest、確認時点を束ね、nativeの支出署名鍵とは別のアプリ用署名鍵とdomainを使う案です。署名の検証は管理者が検査したという証言の検証であり、隠れたnative出力の内容を公開ZK証明で検証することとは違います。Cのwallet確認も、全出力への公開証明ではありません。B、Cを提出に採用する判断は別途レビューし、Aと同じ保証や受賞可能性を主張しません。

## 完成と提出の条件

提出版の最低条件は、1回のオークションが入金、受付、秘密計算、公開証明、署名、送金、返金、受取確認まで通ることです。合わせて、同額、参加者不足、ゼロ入札、無効入力、途中停止、中止返金、期限切れ、取引差し替えを検証します。証明の改ざん検査と実際の取引との対応の検査を、UIの表示だけで代用しません。

提出物には、OSSコード、プロトコル仕様、秘密にする情報の表、信頼条件、測定結果、第三者用の再現手順、実取引の検証資料、短いデモ動画を含めます。デモは「入札 → 価格の証明 → 意図的な改ざんの拒否 → shielded精算と返金」の順で見せます。
